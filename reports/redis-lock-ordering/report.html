Redis 분산 락을 DB 커넥션보다 먼저 획득하면 DB 대기·응답시간이 개선되는가

생성 시각: 2026-09-19T12:39:47.235Z · 대상 커밋: eabac70c740627dd729619d81d4ea77affe2546f · 락 적용 순서: Redis 락 획득 → DB 커넥션·트랜잭션 사용(재고 조건부 UPDATE + 유니크 제약 그대로) → 커밋 완료 → 락 해제(DistributedLockAop, AopForTransaction REQUIRES_NEW)

1. 의사결정 요약

200 req/s: DB 락 대기는 줄었지만(1289→0), 전체 응답시간(p95 2651.0 ms→5929.4 ms)은 개선되지 않았다 - Redis 락 획득 평균 대기 2010.7 ms가 DB 대기 감소분을 상쇄했을 가능성이 있다. DB 대기가 Redis 대기로 자리만 옮겼다면 고객이 기다리는 총 시간은 그대로일 수 있다.

500 req/s: DB 락 대기는 줄었지만(3999→0), 전체 응답시간(p95 5728.0 ms→10000.5 ms)은 개선되지 않았다 - Redis 락 획득 평균 대기 1952.2 ms가 DB 대기 감소분을 상쇄했을 가능성이 있다. DB 대기가 Redis 대기로 자리만 옮겼다면 고객이 기다리는 총 시간은 그대로일 수 있다.

2. 실험 조건

  • 풀 크기는 두 조건에서 동일하게 고정했다(아래 표의 "풀" 값). SQL·재고 조건부 UPDATE·유니크 제약·트랜잭션 경계는 두 조건 동일.
  • MySQL만: mysql-loadtest 프로필(coupon.distributed-lock.enabled=false) - DistributedLockAop 빈 자체가 생성되지 않아 재고별 동시 쓰기가 조건부 UPDATE/유니크 제약만으로 처리된다.
  • Redis 락 → DB: mysql-loadtest,redis-lock-loadtest 프로필 - 같은 Facade 호출이 재고별 Redis 락(획득 대기 최대 5s, 보유 최대 3s) 안에서 실행된다.
  • k6 constant-arrival-rate의 maxVUs를 max(2000, rate*12)로 넉넉히 잡아, dropped_iterations가 k6 설정 자체의 VU 부족이 아니라 서버가 그 요청률을 못 받아내 iteration이 계속 점유돼 있었다는 신호로 해석되게 했다. 아래 표의 "VU 사용" 열이 상한에 근접(⚠︎)하면 이 여유조차 부족했다는 뜻이므로 그 실행의 숫자는 참고만 한다.

4. 읽는 법

  • DB 락 대기 누적 증가는 Innodb_row_lock_waits(누적 카운터)의 실행 시작 대비 끝 값 차이다 - 이 실행 동안 실제로 행 락을 기다린 횟수.
  • Redis 락 획득은 coupon.redis_lock.acquire 타이머의 outcome=acquired 평균이다 - 락을 실제로 얻기까지 기다린 시간. 보유는 coupon.redis_lock.hold - 락을 쥔 채로 DB 작업(커밋 포함)에 걸린 시간. 타임아웃은 waitTime(5s) 안에 획득하지 못해 실패한 건수.
  • DB 대기가 줄었다고 곧바로 "개선"이라 판단하지 않는다 - Redis 락 획득 대기가 그만큼 늘었다면 고객이 체감하는 총 대기시간(HTTP p95)은 그대로거나 더 나빠질 수 있다. §1의 판단은 DB 대기·HTTP 응답시간·실제 처리량 세 가지를 함께 본다.
  • VU 사용률이 상한에 근접한 실행은 k6 자체의 VU 여유 부족이 결과에 섞여 있을 수 있으므로 참고용으로만 본다.

5. 한계

요청률별 1회씩만 실행했다(반복 없음 - 변동폭 미측정). 풀 크기 변화와의 조합, 3회 반복, 자원(CPU/메모리/GC) 상세, 오픈 순간 집중 패턴은 미실행이다. 이 실험은 발급 처리(issueCoupon) 단계만 다루며, 접수 단계(현재 비동기로 분리된 acceptOnly)는 애초에 락을 쓰지 않으므로 대상이 아니다.
