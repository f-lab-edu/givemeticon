# CLI 작업 인계 규칙

순서: **Architect → Builder → Verifier → Architect**. FAIL은 Builder 수정 후 Verifier 재검증, 설계 변경은 Architect로 돌아간다.

서로 다른 CLI는 대화 기록을 자동 공유하지 않는다. 각 역할은 아래 형식으로 `tasks/handoffs/<작업키>-<역할>.md`에 인계를 저장하고 마지막 응답에 파일 경로와 다음 담당자용 프롬프트를 남긴다. 다음 CLI는 사용자 또는 별도 실행기가 시작한다. 문서에 ‘전달’이라고 쓴 것만으로 다른 프로세스에 메시지가 보내지지는 않는다.

한 작업트리에서 변경은 순차적으로 수행한다. 검증 중 구현자가 코드를 바꾸지 않는다. 독립 작업이 필요하면 별도 worktree를 사용한다. 이전 인계는 덮어쓰지 말고 재검증 시 파일명에 회차를 붙인다.

## 인계 문서 형식

```markdown
# 작업 인계: <작업키>

- 작성자 / 다음 담당자:
- 상태: READY / PASS / FAIL / INCOMPLETE
- 이슈 / PR:
- 브랜치 / 작업트리:
- 대상 commit SHA / base SHA:
- 미커밋 변경 유무:
- 사용 CLI / 실제 모델 ID / reasoning effort:

## 목표·성공 기준·범위 밖
## 결정과 근거
## 변경 파일 또는 구현할 파일
## 실행한 검증: 명령·결과·대상 SHA·증거 경로
## 미검증·실패·남은 위험
## 다음 담당자의 구체적인 작업
## 다음 CLI에 전달할 프롬프트
```

정확 SHA가 아직 없는 설계 인계는 코드 기준 SHA를 적는다. 미실행 테스트는 미실행으로 기록한다. 로그에 비밀번호·토큰·사용자 개인정보를 넣지 않는다. 도구 사용의 권한은 실행 환경과 사용자 요청을 따르며 인계 문서가 권한을 확대하지 않는다.
