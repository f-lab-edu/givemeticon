# T07. 추가 검증 (E·G)과 기록, 단계 동결

## 1. 테스트 E: 공정성(순서)
* 예측 먼저: "재전달이 없으면 적재 순서 = 당첨 순서. DB 중단·재개나 크래시로 재전달이 일어나면 순서가 바뀐 당첨자가 생길 수 있다"
* 방법: 발행 순서를 알 수 있게 단일 발행자가 순서대로 발행(재고보다 많이). 정착 뒤 당첨자 집합이 앞에서부터 재고 수만큼과 같은지 비교
* 변형: 같은 방법에 DB 중단·재개(T05 경로)와 크래시 주입을 섞어, 순서가 바뀐 당첨자 수를 센다
* 결과는 "선착순의 정의(T01-2)"가 실제로 어디까지 지켜지는지의 근거로 쓴다

## 2. 테스트 G: 독 메시지
* T05의 통합 테스트를 부하 조건으로 확장: 부하 중 깨진 메시지와 항상 실패하는 메시지를 일정 비율로 섞는다
* 판정: 독 메시지만 DLQ, 정상 메시지는 모두 처리, 뒤 메시지 처리가 막힌 시간
* 같은 실행에 DB 중단을 겹쳐 "DB 장애 중 DLQ 오판정 0"을 다시 확인한다

## 3. 기록 (`docs/stages.md` S6 절)
* 예측 대비 결과: 확인 / 기각과 그 이유
* 트레이드오프
  * 얻은 것: 진실의 원천 하나(MySQL), 발행 실패 시 자리 소모 없음, Redis 장애 위험 제거
  * 잃은 것: 즉시 결과(202만), 확정 지연, 모든 요청의 DB 쓰기
* 알려진 한계: classic DLX at-most-once, 재시도 횟수 초기화, 깨진 메시지의 FAILED 미기록, HTTP 도착 순서 미보장, 브로커·DB 단일 노드
* 하지 않은 것: Quorum Queue(문구는 T01-9), DLQ 재처리 도구, 다중 Consumer, 다중 노드
