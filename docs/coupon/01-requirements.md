# 선착순 쿠폰 시스템: 요구사항과 검증 기준

> 단계: 1 / 요구사항·검증 기준 확정 초안  
> 작성일: 2026-09-22 (한국 표준시)  
> 범위: 요구사항을 설계·구현·성능 검증과 분리해 정의한다. 이 문서는 구현 변경이나 성능 달성을 주장하지 않는다.

## 0. 목적과 문서 상태

이 문서는 포트폴리오에서 **요구사항 → 설계 판단 → 구현 → 검증**을 추적할 수 있도록, 선착순 쿠폰의 고객 약속과 합격 기준을 먼저 고정한다.

- 적용 환경: Java/Spring, MySQL, Redis, 개발·운영 담당 1명.
- 이번 단계의 산출물: 업무 규칙, 측정 정의, 장애 보장 경계, 미정 사항, 현재 구현 차이.
- 이번 단계에서 하지 않는 일: 실행 코드·스키마·운영 설정 변경, 성능 시험 실행, 장애 복구 성능의 입증.
- `PENDING` 등의 현재 코드 상태명은 구현 관찰값일 뿐, 이 문서의 요구사항을 이미 만족한다는 뜻이 아니다.

## 1. 업무 규칙과 반드시 지켜야 하는 불변조건

### 1.1 행사 설정

운영자는 행사 시작 전에 다음 값을 설정한다.

| 항목 | 규칙 |
| --- | --- |
| 행사 시작 시각 | `Asia/Seoul`(한국 표준시, KST) 기준의 명시적인 시각이다. 시작 전에는 신청을 접수하지 않는다. |
| 총수량 | 발급 가능한 쿠폰의 최대 수량이다. 0보다 커야 한다. |
| 고액 쿠폰 수량 | 총수량 이하의 정수다. 100장 행사는 50장으로 설정한다. 1,000장 행사는 운영자가 별도로 설정한다. |
| 고액/일반 금액 | 100장 행사는 각각 10,000포인트/5,000포인트다. 1,000장 행사의 금액·수량 조합은 행사 설정으로 명시해야 한다. |

행사 시작 뒤 설정을 바꾸는 정책은 이번 요구사항만으로 정하지 않는다. 최소한 이미 접수된 신청의 접수 순서, 배정 등급, 결과가 사후 변경되지 않아야 한다.

### 1.2 불변조건

아래 조건은 정상·재시도·복구 처리 모두에서 깨지면 안 된다.

1. 행사별 발급 쿠폰 수는 해당 행사의 총수량을 초과하지 않는다.
2. 행사별 고액 쿠폰 발급 수는 고액 쿠폰 수량을 초과하지 않는다.
3. 동일 계정은 동일 행사에 **접수 레코드 하나**, **발급 쿠폰 하나**만 가질 수 있다. 같은 요청의 재전송은 새 접수가 아니라 기존 접수번호와 현재 결과를 돌려준다.
4. 유효하게 접수된 순번 `1..고액 쿠폰 수량`에는 고액 쿠폰을, 그 다음 순번부터 총수량까지는 일반 쿠폰을 배정한다. 총수량을 넘는 유효 접수는 발급 대상이 아니며 소진 결과를 보존한다.
5. 여러 애플리케이션 인스턴스가 동시에 처리해도 행사 안의 배정·발급은 확정된 접수 순번을 역전하지 않는다. 요청을 보낸 클라이언트 시각, DB 락 획득 순서, Redis 락 획득 순서는 순서 보장의 증거가 아니다.
6. 접수 성공은 발급 성공이 아니다. 접수 후에는 `처리 중`, `발급 완료`, `소진/발급 불가`, `확인 중` 중 현재 결과를 조회할 수 있어야 한다.
7. 통신 응답을 잃거나 재접속해도 본인 접수번호와 최종 결과를 재확인할 수 있어야 한다.
8. 쿠폰 사용에 따른 포인트 적립은 쿠폰 한 장당 한 번만 일어난다. 사용 처리의 재시도·장애 복구가 중복 적립을 만들면 안 된다.
9. 장애 중에는 처리 시간을 단축하려고 확정된 접수·순서·발급·적립 결과를 덮어쓰거나 재정렬하지 않는다.

### 1.3 100장 행사 예시

총수량 100장, 고액 수량 50장일 때 유효 접수 순번 1~50은 10,000포인트 쿠폰, 51~100은 5,000포인트 쿠폰이다. 순번 101 이후의 유효 접수는 쿠폰을 발급하지 않되, 왜 발급되지 않았는지(예: `SOLD_OUT`)를 조회 가능하게 보존한다.

이 예시는 검증용 업무 규칙이며, 현재 구현에서 실제로 이 등급 분배가 동작한다는 측정 결과가 아니다.

## 2. ‘접수 순서’와 ‘접수 완료’의 정확한 정의

### 2.1 접수 순서

**접수 순서**란 한 행사 안에서 서버가 승인한 유효 신청에 부여한, 중복되지 않고 단조 증가하는 `acceptance_sequence`다.

- 순번은 행사별로 1부터 시작하며, 하나의 내구성 있는 트랜잭션에서 신청 레코드와 함께 확정·저장되어야 한다.
- 여러 인스턴스가 처리해도 같은 행사에서 같은 순번을 두 번 부여할 수 없고, 확정된 작은 순번을 건너뛰어 큰 순번의 등급·발급 결과를 먼저 확정하면 안 된다.
- 재시도 요청은 기존 순번을 반환한다. 새 순번을 만들지 않는다.
- 시작 전 요청, 인증 실패, 형식 오류, 이미 접수한 계정의 **첫 요청이 아닌 재전송**은 새로운 유효 순번을 만들지 않는다.
- 클라이언트의 요청 시작 시각, HTTP 도착 순서 관찰값, auto-increment ID만으로는 이 정의를 대체할 수 없다. 실제 순번 데이터와 그 원자적 확정 방식을 검증 증거로 남긴다.

`acceptance_sequence`를 어떤 테이블/제약/트랜잭션으로 원자적으로 만들지는 다음 설계 단계에서 결정한다. 현재 단계에서는 그것이 반드시 보존해야 할 업무 사실이라는 점만 고정한다.

### 2.2 접수 완료

**접수 완료**는 다음을 모두 만족한 순간이다.

1. 행사 시작 시각 이후의 유효 요청임을 확인했다.
2. 행사·계정 조합의 접수 레코드, 접수번호, 접수 순번, 최초 접수 시각이 영속 저장소에 커밋됐다.
3. 호출자에게 접수번호와 조회 가능한 상태를 반환할 준비가 됐다. 네트워크 응답이 유실되어도 같은 계정이 재조회/재시도하면 같은 접수번호를 찾을 수 있다.

따라서 HTTP 응답을 보냈다는 사실만으로 접수 완료가 되지 않으며, 반대로 커밋 뒤 HTTP 응답이 유실된 경우에도 접수는 완료된 것이다. 발급·포인트 적립은 접수 완료의 후속 결과다.

### 2.3 결과 상태의 최소 계약

표현 이름은 구현 단계에서 정하되 고객 및 복구 처리를 위해 다음 의미가 구분되어야 한다.

| 의미 | 조회 응답 예시 | 재처리 원칙 |
| --- | --- | --- |
| 접수·처리 대기 | `PENDING` | 같은 접수번호와 순번을 유지한다. |
| 발급 확정 | `ISSUED` | 쿠폰 식별자·등급을 고정한다. |
| 소진 등 발급 불가 확정 | `SOLD_OUT` 또는 명시적 사유 | 발급으로 되돌리지 않는다. |
| 장애로 결과 미판정 | `CHECKING` | 추측으로 성공/실패를 답하지 않고, 복구 절차로 원장과 쿠폰 상태를 대조한다. |

## 3. 성능 지표의 측정 시작·종료 시점과 성공 판정 기준

### 3.1 정상 상황 목표와 부하 모델

정상 상황의 목표 부하는 **10초 동안 고유 회원 10,000명이 각각 최초 신청 1회**를 보내는 것이다. 이는 평균 1,000 최초 신청/초의 균등 도착 모델이며, 오픈 순간에 완전히 몰리는 별도 집중 패턴을 이미 검증한 것으로 해석하지 않는다.

- 반복 신청과 상태 조회는 최초 신청 10,000건에 포함하지 않고 별도 RPS·건수·비율로 기록한다.
- 부하 도구가 계획한 요청, 실제 요청 시작, 완료, `dropped_iterations`, VU/부하 발생기 CPU·메모리를 함께 남긴다. `dropped_iterations`만으로 VU 부족인지 서버 응답 지연으로 VU가 점유됐는지 단정하지 않는다.
- 각 실행은 새 행사와 격리된 회원 데이터로 수행한다. 실행 ID, 코드 커밋, 설정, 인스턴스 수, 풀·DB 자원, 시간대, 도구 버전을 저장한다.

### 3.2 시간 경계와 단위

| 지표 | 시작 시점 | 종료 시점 | 단위·모집단 |
| --- | --- | --- | --- |
| 최초 신청 도착률 | 부하 도구가 최초 신청 HTTP 요청을 시작한 시각 | 마지막 예정 최초 신청의 시작 시각 | 요청/초, 고유 회원의 최초 신청만 |
| 접수 확인 시간 | 클라이언트가 최초 신청 HTTP 요청을 전송한 시각 | 접수 완료를 나타내는 HTTP 응답을 수신한 시각 | ms, 유효 최초 신청 및 재전송 성공을 분리 집계 |
| 서버 접수 처리 시간 | 서버가 요청을 수신한 시각 | 접수 원장 커밋 뒤 응답을 작성할 수 있는 시각 | ms, 서버 계측. 네트워크·브라우저 시간과 별도 |
| 접수→최종 결과 시간 | 해당 접수의 영속 커밋 시각 | `ISSUED` 또는 발급 불가 결과가 영속 커밋되고 조회 API에서 확인 가능한 시각 | 초, 접수 완료 건별 |
| 행사 결과 소진 시간 | 행사에서 첫 접수 완료가 영속 커밋된 시각 | 해당 행사 접수 완료 건이 모두 최종 상태가 된 시각 | 초, 행사별 |
| 실제 발급 처리량 | 발급 확정 상태가 커밋되는 시각 | 동일 | 건/초. 빠른 소진 응답은 발급 처리량에 넣지 않음 |

브라우저 렌더링까지 측정하지 않으면 ‘고객 화면 표시 시간’은 검증하지 않은 것으로 기록한다.

### 3.3 성공 판정

| 판정 항목 | 정상 상황 합격 기준 | 증거 |
| --- | --- | --- |
| 부하 생성 | 10초에 고유 회원 10,000명의 최초 신청을 실제로 생성했고, 누락·`dropped_iterations`·도구 포화를 별도 보고한다 | k6 원본 결과와 발생기 자원 |
| 접수 확인 | 유효 최초 신청의 95% 이상이 2초 이내에 접수 여부를 안다. HTTP 오류·타임아웃·네트워크 실패는 제외하지 않고 별도 및 전체 비율에 반영한다 | 클라이언트 및 서버 타임스탬프, 응답 유형별 건수 |
| 최종 결과 | **잠정 해석:** 각 접수 완료 건은 접수 커밋부터 최종 결과 조회 가능 상태까지 3분 이내여야 한다 | 원장·상태 조회·작업 로그 |
| 정합성 | 발급 수 = 행사 총수량 이하, 고액 수 = 고액 한도 이하, 행사·계정당 접수 1건/발급 1건, 접수 순번별 등급 일치, 중복 포인트 적립 0건 | DB 검증 쿼리와 원본 스냅샷 |
| 순서 | 발급/등급 확정 결과가 행사별 `acceptance_sequence` 규칙과 일치한다 | 순번·상태·쿠폰 등급 원장 |

‘최초 유효 신청부터 최종 결과 확인까지 3분’이 **행사 전체의 마지막 결과가 3분 안에 확정**되어야 한다는 뜻인지, **각 신청별 3분**이라는 뜻인지는 최종 사업 결정이 필요하다. 표의 잠정 기준은 고객별 지연을 판단하기 위한 후자이며, 행사 전체 마감 SLA를 대체하지 않는다.

성능 합격은 정합성·순서 검증이 통과했을 때만 주장할 수 있다. 한 번의 실행, 로컬 PC, 재고가 빨리 소진된 전체 응답 p95만으로 운영 한계를 일반화하지 않는다.

## 4. 장애 보장 범위: 프로세스 종료와 저장장치 손실의 구분

### 4.1 프로세스 종료·재시작 (영속 저장소가 정상인 경우)

목표 보장은 다음과 같다.

- MySQL 커밋이 완료된 접수 원장·순번·최종 결과는 재시작 뒤에도 조회 가능해야 한다.
- 커밋되지 않은 요청은 접수 완료로 간주하지 않는다.
- `PENDING` 또는 결과가 불명확한 건은 접수번호를 보존하고 `CHECKING`으로 안내할 수 있어야 한다. 복구 작업은 기존 순번을 바꾸지 않고 쿠폰·재고·포인트 원장을 대조해 결과를 확정한다.
- Redis는 접수 사실·순번·최종 결과의 유일한 원장이 아니어야 한다. Redis 락/캐시가 사라져도 MySQL 원장을 바탕으로 안전하게 재개할 수 있어야 한다.

이는 요구되는 보장이지, 현재 구현에서 프로세스 강제 종료 시험으로 이미 입증된 사실이 아니다.

### 4.2 저장장치 손실·DB 손상·리전 손실

애플리케이션 코드만으로는 저장장치 손실 후 접수·순서·결과의 보존을 보장할 수 없다. 이 범위는 MySQL 고가용성 구성, 복제 지연, 백업·복구 절차, 보존 기간, 복구 지점 목표(RPO), 복구 시간 목표(RTO), 운영자 대응 절차의 결정과 실제 복구 훈련이 필요하다.

현재 요구사항은 저장장치 손실까지 ‘반드시 데이터 무손실’이라고 약속하지 않는다. 외부 고객 약속으로 확장하려면 허용 가능한 데이터 손실량과 복구 시간, 백업 검증 주기를 별도로 합의해야 한다.

### 4.3 장애 시 우선순위

장애 중에는 처리 시간 목표를 일시적으로 만족하지 못할 수 있다. 이 경우 중복 발급·초과 발급·순서 변경·중복 적립을 막고, 상태를 `CHECKING`으로 투명하게 안내하며, 원장 기반으로 복구하는 것이 우선이다.

## 6. 현재 구현과 요구사항의 차이

### 6.1 확인한 현재 구현

2026-09-22 코드 스냅샷을 기준으로 다음을 확인했다.

- `POST /api/v1/coupons/requests`는 `coupon_issue_request`에 접수 레코드를 저장하고, `GET /api/v1/coupons/requests/{requestId}`로 본인 결과를 조회하는 비동기 경로가 있다.
- 접수 테이블에는 `(user_id, stock_id)` 유니크 제약이 있으며, 중복 insert는 기존 접수 레코드를 반환하는 방식이다. 쿠폰 테이블에도 회원·재고 조합의 중복 발급 방지 제약이 있다.
- 비동기 워커는 대기 요청을 ID 오름차순으로 읽고, Redis 분산 락이 적용된 처리 메서드에서 발급을 시도한다. 재고 차감은 잔여 수량 조건을 둔 SQL을 사용한다.
- 기존 동기 발급 경로도 남아 있다. 쿠폰 사용의 포인트 이력에는 쿠폰 기준 중복 방지 제약이 존재한다.

위 항목은 소스 코드 관찰값이다. 다중 인스턴스·프로세스 종료·10,000명 부하에서 불변조건이 실제로 유지되는지의 실험 증거는 이번 문서에서 제시하지 않는다.

## 7. 다음 단계의 검증 게이트

구현과 부하 시험을 시작하기 전에 다음을 설계 결정으로 남긴다.

1. 행사·접수·배정·발급·포인트 원장의 식별자와 상태 전이를 정하고, `acceptance_sequence`를 원자적으로 확정하는 방법을 선택한다.
2. 시작 시각·행사 설정 불변성·재시도 UX·3분 SLA의 행사 전체 의미를 제품 결정으로 확정한다.
3. 다중 인스턴스 정합성 시험(동일 계정 중복, 초과 수요, 등급 경계, 순서 역전, 응답 유실)을 먼저 통과시킨다.
4. 그 뒤에만 고정된 구현과 데이터로 10초/10,000 고유 회원 부하를 반복 측정한다. 응답 지연은 DB 커넥션 획득 전 대기, DB 락·SQL·트랜잭션 중 점유, 비동기 대기열·발급 지연으로 나누어 해석한다.
5. 프로세스 강제 종료·재시작 시험과 백업 복구 훈련은 별도 시나리오로 기록한다. 저장장치 손실까지의 보장은 RPO/RTO 합의 전에는 주장하지 않는다.
