# 9단계: 접수→발급→조회→사용→적립 실제 API 연결 검증

> 실행일: 2026-09-26 (KST)
> 선행 문서: [03-admission-validation.md](03-admission-validation.md), [07-issuance-validation.md](07-issuance-validation.md)(§0 이번에 발견·수정한 버그), [08-redemption-validation.md](08-redemption-validation.md)
> 범위: 접수(POST) → 실제 비동기 발급 워커 → 조회(GET) → 사용(POST redeem) → 잔액 반영까지를 SQL 픽스처 없이 실제 API 호출만으로 연결하는 소규모 통합 검증이다. 동시 접수 순서 보존, 재고 소진(SOLD_OUT) 판정, 동시 사용 요청, 강제 실패 롤백, 응답 유실 같은 장애·경합 시나리오는 03/07/08 단계에서 이미 대량의 요청으로 검증했으므로 여기서 반복하지 않는다.

## 결론

3~8단계는 각 단계를 SQL로 만든 픽스처(예: "이미 ISSUED로 확정된 신청·쿠폰")로 시작해 자기 트랜잭션만 따로 검증했다. 이 문서는 그 픽스처를 걷어내고, **실제 접수 요청이 실제 발급 워커를 거쳐 실제 `coupon_award`로 이어지고, 그 쿠폰의 실제 저장값(`points`)이 실제 사용(redeem) 응답의 적립액과 정확히 일치하는지**를 실제 MySQL + 독립 Spring Boot 프로세스 2개에서 확인했다. 회원 2명(고액 쿠폰 1장·일반 쿠폰 1장)에 대해 접수·발급·조회·사용·잔액·재시도 3개 시나리오·17개 판정을 전부 통과했다(2회 연속 실행 모두 PASS).

이 통합 검증 과정에서 **실제 결함을 하나 발견해 수정했다**: 재고가 작은 행사에서 발급 워커가 재고를 한 장 이르게 마감시켜, 마지막 한 장이 접수 자체를 거부당해 영영 발급되지 못하는 버그였다. 각 단계를 격리해서 본 기존 검증들은 이 문제를 잡지 못했다 - 상세 원인·수정 내용은 [07-issuance-validation.md §0](07-issuance-validation.md#0-정정-재고-마지막-1장이-영영-발급되지-않던-버그)에 기록했다.

## 1. 왜 이 검증이 필요한가

각 단계 문서(03/07/08)는 의도적으로 "그 단계의 트랜잭션 경계"만 격리해서 봤다 - 예를 들어 8단계는 이미 `ISSUED`로 확정된 `coupon_award`를 SQL로 직접 만들어두고 사용(redeem) 트랜잭션에만 집중했다. 이 방식은 각 단계의 정합성 증명에는 정확하지만, **단계 사이의 연결 자체**(접수가 실제로 발급으로 이어지는지, 발급된 쿠폰의 실제 값이 사용 단계로 정확히 전달되는지, 시간이 걸쳐 접수가 들어올 때 워커가 올바르게 반응하는지)는 증명하지 못한다. 실제로 이번 검증에서 SQL 픽스처 대신 실제 API 체인을 처음 연결해보자마자 07단계의 격리된 검증으로는 드러나지 않았던 버그(§0)가 나왔다 - 이 문서의 존재 이유 자체가 그 증거다.

## 3. 실제 검증 결과

`scripts/coupon-e2e/validate-two-processes.sh`로 독립 Spring Boot 프로세스 2개(포트 18120/18121, 프로필 `local,coupon-admission,coupon-admission-test,coupon-issuance`) + 전용 MySQL DB에서 실행했다. 행사는 고액 1장 + 일반 1장(총 2장)만 두고, 회원 2명을 순서대로 접수시켜 1번째는 고액(10000), 2번째는 일반(5000)을 받도록 결정적으로 구성했다.

| # | 시나리오 | 판정 수 | 결과 |
| --- | --- | ---: | --- |
| 1 | 접수(POST, 실제 API) → 실제 비동기 발급 워커가 처리 → 조회(GET, 실제 API)로 확인. member_high(1번째)는 실제로 HIGH 등급·10000포인트로, member_normal(2번째)은 실제로 NORMAL 등급·5000포인트로 발급됨을 SQL 개입 없이 확인 | 6 | PASS |
| 2 | 사용(POST redeem, 실제 API) → 적립액이 1번에서 실제로 발급된 `coupon_award.points`와 정확히 일치(고액 10000/일반 5000, 하드코딩된 고정값이 아님). `member_point_balance`도 각각 정확히 일치 | 8 | PASS |
| 3 | 체인 전체의 멱등성: 접수 재요청은 새 신청을 만들지 않고 같은 `requestId`를 반환하고, 사용 재요청은 같은 `redeemedAt`을 반환하며 잔액이 바뀌지 않음 | 3 | PASS |

**17/17 판정 PASS**(6+8+3=17). 2회 연속 실행에서 모두 통과했다. 원본: `build/coupon-e2e-validation/`(재실행 시 갱신됨).

### 3.1 이 스크립트가 하지 않는 것

재고 소진(SOLD_OUT) 판정은 이 스크립트에서 재현하지 않는다. 실제로 처음에는 세 번째 회원을 접수시켜 SOLD_OUT까지 확인하려 했으나, 재고가 2장뿐인 소규모 구성에서는 실제 워커가 너무 빨리 반응해(§0에서 발견한 버그를 고친 뒤에도) 두 번째 회원의 발급이 끝나자마자 행사가 `CLOSED`로 바뀌어, 세 번째 회원의 접수 자체가 (정상적인) 409로 막혀버려 "재고 소진 판정"이 아니라 "이미 마감된 행사에 대한 신규 접수 거절"이라는 다른 경로와 섞였다. 이 경합은 접수와 발급 사이에 충분한 수량 여유가 있어야 결정적으로 재현되며, 그 재현은 이미 07단계(총수량 100에 150명 동시 접수)에서 대량으로 검증했으므로 이 소규모 통합 검증에서는 반복하지 않았다.

### 3.2 재현 명령

```bash
bash scripts/coupon-e2e/validate-two-processes.sh
```

기존 `givemeticon` DB, 다른 단계의 검증 DB는 건드리지 않는다. 전용 DB(`givemeticon_coupon_e2e_validation`)만 매 실행 시 drop/recreate한다.

## 4. 이번 범위에서 하지 않은 것 (미검증 명시)

- **동시 접수 순서 보존, 재고 소진 판정, 동시 사용 요청, 강제 실패 롤백, 응답 유실은 이 문서에서 재검증하지 않았다.** 각각 03/06/07/08단계에서 대량의 요청으로 이미 검증했다 - 이 문서는 "단계 사이의 연결"만 소규모로 확인한다.
- **묶음 접수(6단계)와의 연결은 확인하지 않았다** - 기존 단건 접수 경로만 사용했다.
- **성능 목표(p95 2초 등)는 이 문서의 범위가 아니다** - 회원 2명 규모의 정합성 확인이다.
- `./gradlew test`(단위 테스트)는 이번에도 실행하지 않았다 - 실제 MySQL·두 프로세스 검증 스크립트로만 검증했다.
