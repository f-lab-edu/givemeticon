# 4단계: 접수 API 단독 부하테스트 결과

> 실행일: 2026-09-22 (KST)  
> 검증 질문: **발급 작업 없이 고유 회원 10,000명의 신청을 10초 동안 받아, 접수 확인 p95 2초 이내를 달성할 수 있는가?**

## 결론

**달성하지 못했다.** 최종 측정 3회 모두 k6가 목표 요청을 빠짐없이 생성했지만, 성공 접수 응답의 p95는 **8.707~9.782초**였고, 전체 유효 요청 중 2초 안에 정상 접수 응답을 받은 비율은 **0.61%~1.66%**였다. 클라이언트 10초 타임아웃도 93.1%~96.2% 발생했다.

반면, 각 회차가 정리된 뒤에는 목표 회원의 신청이 모두 MySQL에 `PENDING`으로 저장됐고, 행사별 순번은 1부터 연속이었다. 즉 이 결과는 **정합성은 확인됐지만 고객의 접수 응답 목표는 미달**이라는 뜻이다.

## 고정한 조건과 범위

- 독립 Spring Boot 프로세스 2개: `18080`, `18081`; 같은 MySQL 8.0.46 컨테이너 사용
- `local,coupon-admission,coupon-admission-test` 프로필. 발급/복구 워커는 admission 프로필에서 비활성화했고, 최종 DB에서 모든 신청이 `PENDING`, `coupon` 행이 0건임을 확인했다.
- 테스트 전용 헤더 `X-Coupon-Admission-Test-Member`로 회원을 식별했다. 따라서 이 수치에는 운영 세션/Redis 인증 비용이 포함되지 않는다.
- 행사별 `coupon_event` 행 `SELECT ... FOR UPDATE` → 중복/상태 확인 → 순번 증가와 신청 저장을 같은 MySQL 트랜잭션으로 수행하는 현재 구현을 그대로 사용했다.
- 앱별 Hikari 최대 10, 총 설정상 최대 20 연결. SQL, 인덱스, 트랜잭션 범위, DB 내구성 설정은 변경하지 않았다.
- k6 `constant-arrival-rate`: 1,000 iteration/s, 10초, iteration 하나는 해당 행사에 아직 신청한 적 없는 회원 한 명의 최초 접수이다("신규 회원"은 신규 가입자가 아니라 이 행사에 처음 신청하는 회원을 뜻한다). 회원 ID와 대상 포트를 번갈아 배정했다.
- 워밍업은 별도 행사에서 100 req/s, 2초로 수행했고 아래 수치에서 제외했다.
- k6/두 앱/MySQL은 같은 8 CPU / 16 GiB macOS 호스트를 공유했다. 독립 서버 또는 AWS 처리 한계로 일반화할 수 없다.
- Java: Temurin 21.0.5, k6: 2.2.0, MySQL 격리 수준: `REPEATABLE-READ`, `innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, `innodb_lock_wait_timeout=50`.

## 최종 측정 결과

아래 3회는 k6 시작 시 VU 12,000개를 선할당해 `dropped_iterations=0`을 확인한 유효 측정이다. k6 일정 특성상 1·2회에는 10,001건이 예정됐다.

| run_id | 목표/실제 전송 | dropped | 성공 응답 | 타임아웃 | 성공 응답 p50 / p95 / p99 | 전체 요청 중 2초 내 정상 접수 | 판정 |
|---|---:|---:|---:|---:|---:|---:|---|
| `admission-1000rps-10s-20260922T112231Z-1` | 10,000 / 10,001 | 0 | 383 | 9,618 | 5.676 / 9.782 / 9.954초 | 61 (0.61%) | 실패 |
| `admission-1000rps-10s-20260922T112400Z-2` | 10,000 / 10,001 | 0 | 451 | 9,550 | 2.600 / 8.707 / 9.777초 | 166 (1.66%) | 실패 |
| `admission-1000rps-10s-20260922T112527Z-3` | 10,000 / 10,000 | 0 | 688 | 9,312 | 4.524 / 9.148 / 9.695초 | 130 (1.30%) | 실패 |

- 5xx는 3회 모두 0건이다. 실패 응답은 k6의 10초 요청 타임아웃이다.
- 성공 응답 p50/p95/p99은 `k6.json`에서 HTTP 200인 `http_req_duration` 표본을 정렬해 nearest-rank로 계산했다. 전체 응답의 p50/p95/p99은 타임아웃 때문에 각 회차 약 10초이며, 성공 응답만으로 통과라고 해석하지 않았다.
- 각 실행은 k6가 종료된 뒤에도 앱 풀의 active/pending이 0이고 DB 신청 건수가 연속 표본에서 같아질 때까지 기다렸다. 시작~정리 완료는 각각 89초, 87초, 101초였다. 이는 실행 전체의 정리 시간일 뿐, 고객별 최종 결과 3분 목표를 검증한 값은 아니다.

## DB 정합성 검증

| run_id | DB 신청 | 고유 회원/순번 | 순번 범위·행사 카운터 | PENDING / 비-PENDING | 중복 회원·순번 | 쿠폰 행 | 결과 |
|---|---:|---:|---|---:|---:|---:|---|
| `...112231Z-1` | 10,001 | 10,001 / 10,001 | 1~10,001 / 10,001 | 10,001 / 0 | 0 / 0 | 0 | 통과 |
| `...112400Z-2` | 10,001 | 10,001 / 10,001 | 1~10,001 / 10,001 | 10,001 / 0 | 0 / 0 | 통과 |
| `...112527Z-3` | 10,000 | 10,000 / 10,000 | 1~10,000 / 10,000 | 10,000 / 0 | 0 / 0 | 통과 |

각 `applications.tsv`의 회원 ID 범위도 생성 범위 전체와 같았다. 즉 성공 응답을 받은 회원은 모두 DB에 존재하며, 응답을 받지 못한 대다수도 최종적으로 커밋됐다. 예를 들어 3회차는 9,312건이 타임아웃이었지만, 최종 DB 신청은 10,000건이다. 이는 **응답 유실/클라이언트 타임아웃과 DB 커밋을 정합성 오류로 같은 취급하지 않은** 근거다. 다만 성공 응답별 request-id를 원본에서 별도로 대조하지는 못했으므로, 개별 응답-행 매핑은 미측정이다.

## 병목 관찰

### 확인한 사실

- 각 앱의 부하 중 스냅샷에서 Hikari는 `active=10/max=10`, `pending=189`, 연결 획득 타임아웃 누적 0이었다. 두 풀 모두에서 풀 획득 전 대기가 존재했다.
- MySQL `sys.innodb_lock_waits` 표본에는 같은 `coupon_event` 기본키를 대상으로 한 `SELECT ... FOR UPDATE` 대기/차단 SQL이 3회차 기준 표본 488~625행(시점별 중복 포함) 기록됐다. `data_lock_wait_rows`의 관찰 최대값은 190이었다.
- `Innodb_row_lock_waits` 누적 증가는 실행별 591, 1,044, 963이었다. 누적 지표이며 1초보다 느린 폴링 표본도 있어 전체 대기 횟수로 해석하지 않는다.
- DB 처리 완료 건수는 포트별로 균등했다. 회원 ID의 포트 배정 기준으로 1·2회차는 5,001/5,000건, 3회차는 5,000/5,000건이 저장됐다.
- 관찰 시점 앱 CPU는 대략 7~59%, MySQL 컨테이너 CPU는 32~64%, DB 메모리는 약 776~792 MiB였다. 같은 호스트의 k6 CPU/메모리와 JVM GC, 디스크 I/O 지연은 충분히 측정하지 못했다.

### 해석 (가설)

행사 하나의 행을 모든 접수가 직렬로 잠그는 구조라서, 해당 행의 InnoDB 락 대기와 20개 연결의 점유가 함께 발생한 것으로 보인다. Hikari pending과 실제 차단 SQL이 함께 관찰됐으므로 단순히 “풀 크기가 작다”만으로 설명할 수 없다. **행사 행 락의 직렬화, DB/앱의 커넥션 점유, 같은 장비 자원 경쟁이 어느 정도씩 기여했는지는 이번 측정만으로 분리하지 못했다.**

트랜잭션/커밋 타이머를 추가했지만, 이번 원본의 `after.prom`은 요청 정리 전 스냅샷이다. 완료된 모든 요청의 트랜잭션 p95·커밋 p95는 산출하지 않았으며 미측정으로 남긴다. 이후 스크립트는 quiescent 시점 Prometheus 스냅샷도 저장하도록 보완했다.

## 발생기 보정 이력

초기 6회는 6,000 VU 선할당(최대 12,000)으로 실행했다. 실제 전송이 6,035~8,466건이고 `dropped_iterations`가 1,535~3,966건이어서 목표 1,000 req/s 검증으로 사용하지 않았다. 원본은 `runs/admission-1000rps-10s-20260922T110344Z-1`부터 `...111021Z-3`에 보존했다. 최종 3회는 선할당을 12,000으로 올려 누락 0건을 확인했다. 이는 앱 성능 튜닝이 아니라 발생기 용량 보정이다.

## 미검증 및 다음 한 가지 후보

- 운영 인증, 브라우저 화면 표시 시간, 발급/포인트 적립, 장애 복구, 3분 고객별 최종 결과, 장시간 안정성은 범위 밖이거나 미측정이다.
- Hikari 획득 대기시간 분포, JVM GC, 디스크 I/O 지연, 완결된 트랜잭션/커밋 분포는 현재 원본만으로 미측정이다.
- 다음 변경 후보는 **접수 트랜잭션에서 행사 행을 잠근 채 수행하는 SQL과 비-DB 작업의 범위를 계측해 최소화할 수 있는지 검토**하는 것이다. 이번 결과는 같은 행사 행의 락 대기를 직접 보였지만, 풀만 키우는 것이 고객 지연을 줄인다는 근거는 아직 없다. 이 변경은 별도 실험에서만 한다.

## 재현 방법과 원본

```bash
bash scripts/coupon-admission/run-admission-loadtest.sh
```

실행은 전용 DB `givemeticon_coupon_admission_loadtest`만 생성/삭제하며, 기존 DB를 삭제하지 않는다. 원본은 이 문서와 같은 `기록/coupon-admission-loadtest/` 아래에 있다.

- `environment/environment.txt`: 버전, 자원, 내구성 설정, 풀 시작값
- `runs/<run_id>/k6-summary.json`, `k6.json`, `k6-failures.log`: 발생기 원본
- `hikari.csv`, `mysql.csv`, `locks/*.tsv`, `resources.csv`: 서버/DB 표본
- `consistency.tsv`, `applications.tsv`, `completion-poll.tsv`: 종료 및 정합성 근거

`기록/`은 저장소에서 무시되는 로컬 포트폴리오 산출물이다. 비밀값이나 운영 회원 정보는 포함하지 않았다.
